# HTML report presentation rules

- Treat `paper_data.json` as the only data source and never modify extracted values during rendering.
- Replace the separate hero title, summary cards, and basic-information panel with one compact article-information table immediately above the main data. Use the same 12 px base size as the main table. Include title, DOI, journal/year, paper ID, main/SI coverage, scope, compound count, condition count, evidence count, and review count. Render the title and DOI in bold and the DOI in red.
- Render the `文章信息 · paper ID` summary bar at Chinese Small Three (`15pt`, normally 20 CSS px); keep the cells inside the article-information table at their compact base size.
- Do not display the raw JSON or the rate-constant calculation block in the human-facing HTML. Keep both in the canonical JSON for machine use and audit.
- Keep one independent sample/condition record per JSON object, but render one visual table row per compound within a paper. Put all reported values for the same physical quantity in the same column, including film/solution, RT/77 K, and other reported conditions.
- Use compact columns comparable to a literature spreadsheet: Compound, Host, doping ratio, Type, yields, wavelengths, lifetimes, and reported rate constants. Omit Row ID and long condition prose from the main comparison cells.
- Render the complete main table at Chinese Small Four (`12pt`, normally 16 CSS px), including headers, compound rows, paper-note rows, condition footnotes, and the innovation row. Keep citation links and condition markers smaller as secondary annotations.
- For physical-quantity column headers, use 14pt normal-weight Times New Roman. Italicize only the principal symbol (`λ`, `τ`, `Φ`, or `k`) and keep every subscript upright/non-italic. Leave non-physical headers such as Compound, Host, doping ratio, and Type unchanged.
- Treat `Host` and doping ratio as formulation columns: show each unique non-solution host and solid-film doping ratio only once per compound, without condition markers. Do not put a solution solvent or solution concentration in these two columns. Keep solution solvent/concentration in JSON and state them only in the condition footnotes attached to the corresponding spectral or lifetime values.
- Append a short condition marker such as `[a]`, `[b]`, or `[c]` to every displayed value. Explain matrix/solvent, doping/concentration, phase, temperature, atmosphere, and any sample-level excitation in full-width footnotes below the compound rows. Never hide a reported 77 K or solution value merely to simplify the table.
- When a main-table cell contains multiple values or formulations from separate records/conditions, put each entry on its own line with no slash separator. Keep slashes only when they are part of one scientific label or one author-reported value, such as `RTP/TADF` or a rate-constant ratio.
- Keep each displayed value, its condition superscript, and its evidence ID on one unbreakable line in this order: `value` + superscript marker + one space + `[Exx]`. Render main-table evidence IDs in light gray `#9CA3AF`; allow columns to widen rather than splitting this group across lines.
- Normalize the main-table Type column to only `RTP` and `TADF`. If both are supported for a compound, show `RTP/TADF`; if neither is supported, show `Tranditional-F`. Never display `F`, `DF`, `F/RTP`, or other mixed labels in this column. Preserve the full author-assigned wording in JSON and evidence.
- Abbreviate matrices and solvents in the main table, including `PMMA`, `PVA`, and common solvent abbreviations such as `Tol`. Preserve the full source wording in JSON, evidence, and condition footnotes.
- Keep main cells compact: show a reported average lifetime when available, otherwise a reported longest component, otherwise the component range. Compress semicolon-separated wavelength series to a range. Preserve every component and wavelength in JSON and the Evidence Ledger; never overwrite source data with the display summary.
- Detect a doped-matrix record from a reported non-solution host/matrix plus a reported doping ratio; do not hard-code matrix names such as PMMA or PVA. Render its explicitly RT `λP`, `τP`, and `ΦP` in red, and render the corresponding explicitly 77 K values in pure blue `#0000FF`. Among all doped-matrix RT records in the paper, render the longest `τP` and highest `ΦP` in bold and underlined. Among all doped-matrix 77 K records, render the longest `τP` in bold without adding an underline. Do not include solution or temperature-uncertain records in coloring or comparisons.
- Render the logic skeleton, core argument, and one-sentence innovation as three full-width rows after the condition footnotes, in that order. Give all three the same light-blue module background and place them directly together. Link synthesized claims to paper-level evidence.
- Use scientific HTML labels with subscripts: `λ<sub>P</sub>`, `τ<sub>P</sub>`, `Φ<sub>P</sub>`, `k<sub>ISC</sub>`, and analogous fluorescence/delayed-fluorescence labels. Never expose snake_case field names to readers.
- Apply the same scientific-label formatter to manual-review text, including forms such as `PhiF`, `PhiP`, `tauP`, and `lambdaP`; render them as `Φ<sub>F</sub>`, `Φ<sub>P</sub>`, `τ<sub>P</sub>`, and `λ<sub>P</sub>`.
- Show reported metrics prominently and keep missing fields out of the visual comparison area. This is a display choice only; do not remove missing statuses from JSON.
- Render evidence as a compact single-column list, never as cards or a multi-column grid. Put evidence ID, row/object, field label, source location, extraction type, and confidence on one horizontal line; place the short source cue or review warning directly below only when needed.
- Keep high-confidence evidence entries index-like: for table evidence show only the table identifier and location; for non-table evidence show only the first 6–10 source words. Do not repeat the extracted value or display a review note for high-confidence evidence. Show the extracted value, complete short quote, and a prominent manual-review warning only for medium/low-confidence evidence.
- Merge the Evidence Ledger and manual-review list into one bordered review region. For a single paper, keep the article-information table and the combined main-data/review region open. For a multi-paper consolidated report, keep every article-information table open but wrap that article's main data plus combined evidence/manual-review region in one closed `<details>` element. Never place evidence from different papers in the same unscoped anchor namespace.
- Make every evidence citation in the main view link to its Evidence Ledger list entry.
- Use a clean research-review layout without gradients, animation, decorative illustrations, or external assets.
